# Автоматическое определение остатка после импорта

## Причина и решение

Изучены CSV/XLSX импорт, Transaction, нормализация, ForecastResult, кассовые разрывы,
API, frontend, тесты и оба оригинала. Раньше прогноз по умолчанию использовал
текущую дату и брал balance_eod только при наличии операции за эту дату.
На 24.10.2026 данных не было: файлы заканчиваются 30.09.2026. Поэтому баланс
не подменялся нулем, но автоматический пользовательский сценарий не давал
абсолютного прогноза. Отдельной сверки всей выписки при импорте не было.

Теперь импорт определяет и проверяет остатки, сохраняет метаданные в существующем
состоянии приложения, а прогноз без явной даты строится от последнего дня
выписки. Для поздней явно выбранной даты правило неизвестного баланса сохранено.
Старое значение не выдается за баланс текущего дня. Новая финансовая модель,
новый детектор разрывов и хранилище не создавались.

## Алгоритм и точность

В проектах суммы положительны, direction хранит income/expense. При сверке
income дает плюс, expense — минус ровно один раз. Все расчеты через Decimal
с достаточной локальной точностью, без float, допусков и изменения исходных сумм.

1. Отдельный начальный остаток CSV берется при наличии. Используется существующий
   словарь заголовков с минимально добавленными aliases. Непустые значения
   столбца должны совпадать. Начальный остаток не вычисляется вместо явно
   указанного: с ним проверяются предоставленные балансы и выводится конец истории.
2. balance_eod — остаток на конец дня, повторенный у операций. По дате
   агрегируются все фактические поступления/списания. Из первого конечного
   остатка вычитается чистый поток первого дня. Проверяются все следующие
   дневные переходы. Разные остатки одного дня дают invalid.
3. Для явно названного balance_after сортируются разные даты. До первой
   операции: after − amount для income, after + amount для expense. Затем
   сверяется вся цепочка. При одинаковых датах нет времени/достоверной
   очередности — unknown, сортировка по ID не используется как доказательство.
4. Нет исходных балансов — unknown. Пустой/отсутствующий баланс остается null.
   Начальный остаток из файла без конечных балансов позволяет рассчитать
   конец истории по ее фактическим операциям; сами Transaction.balance
   не заполняются расчетными значениями.

Порядок исходных транзакций и source_rows не меняется. Для дневной сверки порядок
внутри даты не нужен. Неизвестные и invalid остатки не становятся нулевыми.
Статусы: detected, provided, unknown, invalid; источник, даты и issues доступны
в balance_info импорта и прогноза. Некорректный непустой текст суммы по-прежнему
отклоняется. Пустые балансы теперь разрешены как отсутствие данных.

## Две разные границы

Остаток до начала выписки — statement_opening_balance. Остаток после всех
исторических операций — statement_closing_balance. Начало прогноза после
выписки использует второй. Это не повторный расчет начального капитала:
он уже перенесен через историю и не должен повторно прибавляться.

Без as_of выбирается последний день доступных операций не позже текущей даты
проекта; as_of_source=statement_end. При пустой истории используется текущая
дата, но баланс неизвестен. При явном as_of анализируются только операции
не позже него, без утечки будущих сумм. Баланс доступен лишь на конец известной
истории; пропуск между последней датой и as_of не объявляется отсутствием операций.

Существующий ручной opening_balance имеет приоритет как остаток на конец
даты расчета. Это отдельный источник provided в прогнозе, не отдельное поле
начального остатка CSV. Диагностика invalid выписки при ручном вводе не скрывается.

Sprint 4 считает balance = opening_balance + cumulative_cash_flow один раз.
Sprint 5 получает тот же ForecastResult и не строит свой баланс. Категоризация,
регулярность, распределение потоков и критерий разрыва <0 не менялись.

| Статус | detected | detected |
| Начало истории | 2024-10-01 | 2024-10-01 |
| Конец истории / дата расчета | 2026-09-30 | 2026-09-30 |
| До начала выписки | 6484608.48 | 400854.05 |
| На начало прогноза | 3756563.37 | 518152.13 |
| Поступления за 30 дней | 8448890.98 | 1822130.74 |

| Кассовые разрывы | 0 | 0 |

Период прогноза обоих файлов: 2026-10-01 … 2026-10-30. Это исторический срез,
явно подписанный в интерфейсе, а не утверждение об актуальном состоянии счета.
На явно выбранную дату 2026-10-24 без предоставленного баланса результат
кассовых разрывов остается not_available. Никакой прогноз между этими датами
не используется как выдуманный фактический баланс.

Пример C071: первая операция — расход 1990.00, остаток ее дня 6482618.48.
До начала выписки: 6482618.48 + 1990.00 = 6484608.48. После всей истории остается
3756563.37. Для 01.10.2026 существующий прогноз дает поступления 281629.70 и
расходы 155930.93: баланс 3882262.14. Через 30 дней:
3756563.37 + 8448890.98 − 9133074.70 = 3072379.65.
Дефицита нет во всех 30 строках, а не только в последней.

У C015 уже в первый день несколько операций: остаток 429282.40 — общий EOD,
поступления дня суммарно 28428.35. Поэтому начальный остаток 400854.05,
а вычитание только первой операции было бы неверным.

## Тестирование и ограничения

Пройдено **333 pytest-теста, 10 Node-тестов и 11 browser-сценариев**. Падений нет.
Сохранены проверки предыдущих спринтов; старый сценарий отсутствия обязательного
balance изменен согласно новой задаче: теперь он проверяется как допустимый
unknown отдельными тестами. NaN/None/пустые ячейки проверяются как пропуск,
Infinity и неверный непустой текст — как ошибка, нулевой баланс — как известное значение.

Проверены: явный остаток и его конфликт, первая операция income/expense,
дневные и послеоперационные балансы, одинаковые даты без очередности, обратный
порядок, отсутствие поля/ячейки баланса, точная передача в прогноз, известный
ноль, повторный и неудачный импорт, отсутствие накопления, настоящий синтетический
дефицит и положительный баланс. Для исходного остатка CSV 100000 и трех расходов
по 30000 к концу истории остается 10000; в следующем месяце прогнозируемый
расход 30000 создает дефицит 20000. Это отдельный синтетический тест, не изменение
реальных CSV. Оба оригинала проверены полностью, контрольные суммы неизменны.

Browser QA на Edge подтвердил автоматические значения обоих CSV, доступный анализ
разрывов, повторный импорт без изменений, честную недоступность на позднюю дату,
XLSX из C071, ошибки модулей и прежние сценарии. Финансовые числа на frontend
не вычисляются. Осталось прежнее предупреждение Starlette о тестовом HTTPX.

```powershell
.\.venv\Scripts\python.exe -m pytest -c pytest.ini backend/tests -q --dataset-dir "C:\Users\nises\Downloads\Telegram Desktop"
npm.cmd --prefix frontend test
npm.cmd --prefix frontend run check
.\.venv\Scripts\python.exe -m scripts.analyze_balances --dataset-dir "C:\Users\nises\Downloads\Telegram Desktop" --output docs/automatic_balance_results.json
.\.venv\Scripts\python.exe -m scripts.test_frontend_browser --dataset-dir "C:\Users\nises\Downloads\Telegram Desktop" --report docs/automatic_balance_browser_results.json
```

Проблема автоматического сценария решена для обоих предоставленных датасетов.
Ограничения: сверка предполагает полный список операций одного счета; совпадение
арифметики не доказывает полноту выписки. Послеоперационный формат без очередности
одного дня не подтверждается. При отсутствии исходных данных остаток неизвестен.
Текущий баланс после конца истории не восстанавливается из предположений.
Хранение осталось временным, алгоритмы прогноза и разрывов не переписаны.
