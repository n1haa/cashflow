# Sprint 5 — анализ потенциальных кассовых разрывов

## Реализация и источник

Изучены структура проекта, Transaction, категории, регулярные группы, ForecastResult,
расчет остатка, текущий API, запуск и тесты. Все 264 проверки Sprint 1–4 проходили
до изменений. Исходные датасеты доступны: C071.csv — 614 операций, C015.csv — 2455,
оба за 2024-10-01 … 2026-09-30. Финансового порога/резерва в проекте нет.

Новый сервис принимает только готовый ForecastResult Sprint 4; он не импортирует
и не вызывает построитель прогноза. Модели транзакций, регулярности и самого
прогноза не менялись. Анализ определяет отрицательные дни, объединяет периоды,
рассчитывает минимальный остаток/дефицит/длительность/восстановление и возвращает
контекст имеющихся потоков. Исходные показатели, записи и состояние не меняются.

## Алгоритм

Сначала проверяются даты, полнота заявленного календарного окна и конечность
денежных значений. Данные сортируются без изменения исходного списка. Дневные
поступления, расходы, компоненты, чистые потоки, остатки и сводка проверяются
на согласованность; некорректный прогноз не исправляется, возвращается
not_available. Новый независимый прогноз не строится.

Отрицательный остаток (<0) открывает период. Следующие соседние отрицательные
дни его продолжают. Первый остаток >=0 завершает период и задает recovery_date;
нулевой остаток — восстановление. Последующее снижение образует новый период.
Если конец окна остается отрицательным, статус ongoing и recovery_date=null:
неизвестно, когда и произойдет ли восстановление за пределами прогноза.

Максимальный дефицит = abs(минимальный отрицательный остаток). Например, при
остатках -10, -50, -20 дефицит равен 50, а не 80. Длительность = календарное
расстояние между первым и последним отрицательными днями +1; день восстановления
не считается отрицательным. Денежные значения — Decimal, без округления исходных
значений и суммирования отрицательных остатков. Порог резервов не добавлялся.

Анализ имеет статусы detected / no_gaps / not_available, отдельные периоды —
recovered / ongoing. При неизвестном исходном или дневном балансе кассовый
разрыв определить нельзя: has_cash_gap и счетчики/сумма дефицита равны null.
Это отличается от no_gaps с нулевыми счетчиками. Доступные дневные изменения
потока возвращаются без подстановки неизвестного баланса нулем.

Если исходный остаток уже отрицателен, фактическое начало до окна не выводится.
При отрицательном первом дне группа помечается starts_before_forecast; начало
и длительность в ответе описывают наблюдаемую часть. При восстановлении уже
в первый день первоначальный минус не создает вымышленный будущий разрыв.

Неполный заявленный период, дубли или пропуски дат дают not_available, чтобы
не соединить разрывы через неизвестные дни. Короткий, но полный заявленный
горизонт анализируется с ограничением только на доступные даты. API Sprint 4
в штатном режиме предоставляет 30 дней.

## Влияющие потоки и ограничения причинности

Для каждой группы используются готовые ForecastDay дня начала и восстановления,
до семи предшествующих дней, день максимального расхода в этом контексте и
ForecastEvent из scheduled_events. Данные не копируются в новые транзакции.
Указываются категории только конкретных связанных регулярных расходов;
исторические средние имеют лишь дневные агрегаты, их категории по дням не
восстанавливаются искусственно. Поступления дня восстановления показываются
как часть дневного результата, без предположений о внутридневном порядке.

Это контекст изменения прогнозируемого остатка, а не доказанная причина разрыва.
У соседних групп контекст может пересекаться: одно событие не становится новым
платежом и не должно повторно суммироваться. События за пределами доступного
прогноза не добавляются. При отсутствии событий остаются дневные суммы.

одного отрицательного чистого потока. Тридцать дневных строк потоков сохранены
в ответе, но analyzed_days=0: проверка отрицательных абсолютных остатков невозможна.

Проверены все дневные остатки, а не только конец окна. В этом историческом
сценарии отрицательных дней нет, поэтому примеров найденных реальных разрывов
нет. Исходные суммы/балансы не уменьшались ради демонстрации. Сценарии обнаружения
проверены отдельно на синтетических прогнозах: один отрицательный день,
несколько соседних дней, восстановление до нуля, два отдельных разрыва,
отрицательный конец окна и дефицит, начавшийся до прогнозного периода.

среза каждого файла, контрольные суммы оригиналов, ограничения и дневные данные.
Не добавлены имена физических лиц и полные назначения. Проверено совпадение
анализа сервиса и API с исходным прогнозом, неизменность файлов и состояния.

```powershell
curl.exe http://127.0.0.1:8000/api/forecast/cash-gaps
curl.exe "http://127.0.0.1:8000/api/forecast/cash-gaps?as_of=2026-09-30"
```

Endpoint принимает существующие as_of и opening_balance. Для одного запроса
прогноз Sprint 4 строится ровно один раз зависимостью get_forecast; новый сервис
анализирует полученный объект. Ошибки параметров сохраняют 422/400 Sprint 4.
Отсутствующие данные возвращают 200/not_available с объяснением, без traceback.
Предыдущие endpoints и формат самого прогноза сохранены.

Фрагмент ответа для текущего среза обоих файлов:

```json
{
  "status": "not_available",
  "has_cash_gap": null,
  "analyzed_days": 0,
  "opening_balance": null,
  "gap_count": null,
  "maximum_deficit": null,
  "gaps": []
}
```

Полный ответ также включает исходные дневные показатели и ограничения.
При известном остатке ответ содержит минимум окна, дату первого разрыва, число
отрицательных дней, список периодов с длительностью/восстановлением и контекстом.
no_gaps означает лишь отсутствие отрицательных остатков в предоставленном
прогнозном сценарии. Если сама модель Sprint 4 предупреждает о нехватке истории,
эти предупреждения сохраняются; положительный сценарий не доказывает отсутствие
реальных будущих обязательств.

## Тестирование и статус

Полный прогон: **305 пройдено, 0 упало**, включая все 264 теста Sprint 1–4.
Проверены пустой/неполный прогноз, ноль, положительные/отрицательные остатки,
один/несколько/раздельные разрывы, восстановление и открытый конец, исходный минус,
неизвестный дневной/исходный баланс, неверные даты/суммы, согласованность,
короткий горизонт, сортировка, очень большие и копеечные Decimal, контекст
крупных расходов и поступлений, отсутствие конкретных событий, CSV/XLSX, оба
оригинала и неизменность предыдущих спринтов. Отдельно проверено, что сервис
не вызывает построитель прогноза, а API вызывает его ровно один раз.

```powershell
.\.venv\Scripts\python.exe -m pytest -c pytest.ini backend/tests -q --dataset-dir "C:\Users\nises\Downloads\Telegram Desktop"
.\.venv\Scripts\python.exe -m scripts.analyze_cash_gaps --dataset-dir "C:\Users\nises\Downloads\Telegram Desktop" --as-of 2026-10-24 --reference-as-of 2026-09-30 --output docs/sprint5_results.json
```

Без каталога оригиналов 14 внешних тестов пропускаются. Остается прежнее
предупреждение Starlette о тестовом HTTPX; новых зависимостей нет.
Sprint 5 завершен для текущего MVP. Кодовых блокировок нет; для достоверного
абсолютного анализа на текущую дату нужен текущий баланс. Результат наследует
ограничения Sprint 4: средние, неполная/устаревшая история, возможное прекращение
регулярных серий. Внутридневные дефициты не определяются по дневным данным.
ongoing означает отсутствие восстановления до конца окна, а не вычисленную
дату восстановления за его пределами. До- и послепрогнозная длительность неизвестна.

Новый прогноз, ML, AI API, финансирование, управление платежами, перемещение
денег, уведомления, frontend и следующий спринт не реализовывались.
