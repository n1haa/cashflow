# Sprint 2: категоризация финансовых операций

## Реализация и границы

Изучены текущие модели, API загрузки и чтения, нормализация, 113 тестов Sprint 1
и оба полных оригинала C071/C015. В каждом CSV девять столбцов; готовой категории
нет. Для категоризации доступны `description`, `direction`, `counterparty`,
сумма, ИНН, дата и остаток. Правила используют первые три; суммы не меняются.
Загрузка и финансовая модель не переписывались. Новых зависимостей нет.

Результат — метаданные по ID той же Transaction, не параллельная финансовая
модель. Категоризация выполняется после загрузки через новый POST
`/api/transactions/categorize`, поскольку существовавшие endpoints только
импортировали и читали операции. Можно обработать все операции или JSON-выборку
`{"transaction_ids":[1,2]}`. Повторный вызов не создает платежи. Метаданные
сохраняются в существующей памяти экземпляра приложения рядом с операциями.

## Алгоритм rules-v1

1. Для поиска: NFKC, единый регистр, ё/е, пунктуация и пробелы. Исходные описания
   не меняются; повторяющиеся буквы не удаляются, чтобы не исказить слова.
2. Каждое правило проверяет направление и регулярное выражение назначения.
   Общее правило комиссии дополнительно требует банковский контекст контрагента.
   ИНН не служит справочником категорий; пустой ИНН не мешает анализу назначения.
3. Выбирается максимальный приоритет: самостоятельный возврат 120, личный вывод
   110, собственный перевод 100, неясный перевод 90, банковская комиссия 80,
   аренда оборудования 70, специальные платежи 60, прочие предметные правила 50,
   клиентская оплата 10. Числа — порядок правил, не уверенность.
4. При равном приоритете разных категорий — `unknown/needs_review` со списком
   правил. При отсутствии совпадения — `unknown/undefined`. Явно неясный перевод
   также требует проверки. Совпадения одной категории не создают конфликт.
5. Назначение дает `automatic` и `is_automatic: true`, иначе false. Сохраняются
   версия правил, коды правил и объяснение. Никаких случайных процентов нет.

Приоритет защищает возврат от попадания в обычную оплату, собственный перевод
от попадания в расходы поставщиков и аренду POS от общей аренды. Для
эквайринга/СБП учитывается смысл всей входящей операции: упоминание удержанной
комиссии или возврата в тексте реестра не превращает зачисление в расход.
«Без НДС» и «Без налога (НДС)» сами по себе не означают налоговый платеж.

Входящие возвраты и исходящие возвраты предусмотрены, но самостоятельных
операций возврата в предоставленных оригиналах нет: эти ветки проверяются
синтетическими тестами. «Прочие поступления» применяется только при явном
страховом возмещении; неизвестные операции в нее не попадают. Категории логистики
и прочих расходов не вводились без оснований в назначениях.

## Проверки и воспроизведение

Полный запуск с каталогом оригиналов: **174 пройдено, 0 упало**. Все 113 тестов
Sprint 1 сохранены. Пройдены базовые сценарии, входящие/исходящие операции,
возвраты, переводы, комиссии, отсутствие правила, неизвестный контрагент,
Unicode/пробелы/регистр, приоритеты и конфликты, обработка CSV/XLSX, API и оба
оригинальных датасета. Нулевая сумма по контракту Transaction запрещена — это
проверяется валидацией, а не обходится ради категории. Пустое описание также
отклоняется Sprint 1; устойчивость сервиса к старой пустой записи проверена отдельно.

Тесты оригиналов проверяют распределение, связь с каждым существующим ID,
неизменность финансовых полей, результат POST/GET, повторную категоризацию без
дублирования и неизменность файлов. Фиксированное распределение — регрессия
правил, не независимая экспертная разметка. Одно предупреждение Starlette об
устаревающем использовании HTTPX в TestClient осталось от Sprint 1.

```powershell

.\.venv\Scripts\python.exe -m scripts.analyze_categorization --dataset-dir "C:\Users\nises\Downloads\Telegram Desktop" --output docs/sprint2_results.json
```

Без внешнего каталога четыре теста оригиналов пропускаются. Исходные операции
не копируются в тестовые fixtures. Команды запуска сервера и примеры API — в README.

## Ограничения и статус

Sprint 2 завершен для текущего MVP и двух предоставленных датасетов; блокирующих
проблем не обнаружено. Правила прозрачны и детерминированы, но не понимают
произвольный язык и могут ошибаться на новых формулировках, отрицаниях и сложных
смешанных платежах. Приоритеты не заменяют экспертную оценку бухгалтерской сути.
Категории описывают назначение потока, а не налоговую/бухгалтерскую проводку.
Дробление платежа, ручной редактор и словарь коррекций не реализовывались.

Сохраняются ограничения Sprint 1: 101 пустой ИНН, один worker, одна последняя
выписка, отсутствие постоянного хранения. Категории очищаются при новой загрузке
и перезапуске. Сводка выбранных ID относится только к выборке. Финансовые суммы
не суммируются и не модифицируются; float используется только для доли покрытия.

Прогнозы, регулярные операции, кассовые разрывы, ML, внешние AI API, интерфейс
и другие задачи Sprint 3 не добавлялись.
