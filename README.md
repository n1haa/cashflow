# CashFlow AI — Sprint 1–3

Backend для загрузки, проверки и категоризации банковской выписки малого бизнеса.
Sprint 1 подготавливает единые данные, Sprint 2 назначает категории объяснимыми
правилами без ML и внешних AI API. Sprint 3 выявляет повторяющиеся операции,
их периодичность, среднюю сумму и следующую ожидаемую дату. Стек: Python 3.10+
(проверяется на установленном Python 3.10.11), FastAPI, Pydantic 2, Pandas,
openpyxl, python-multipart. Сервер — Uvicorn, тесты — pytest и HTTPX.

Linux/macOS: вместо `.\.venv\Scripts\python.exe` используйте `.venv/bin/python`.

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

Проверка обоих полных исходных датасетов без копирования их в репозиторий:

считается ошибкой теста. Подробный анализ, таблицы соответствия и результаты:
[docs/dataset_analysis.md](docs/dataset_analysis.md).

## Входная выписка

CSV в UTF-8 или UTF-8 с BOM, разделитель `;` или `,`. Поля с разделителем внутри
должны быть заключены в двойные кавычки. Неоднозначные разделители и строки с
разным количеством полей отклоняются. XLSX: таблица на первом листе,
заголовок в первой строке. Максимальный размер файла — 10 MiB (10 × 1024² байт),
распакованного XLSX — 100 MiB. Размер проверяется до табличного разбора;
multipart-загрузка может предварительно буферизоваться Starlette на диск.

| Поле | Примеры заголовков | Значения |
| --- | --- | --- |
| `date` | Дата, Дата операции, Operation Date, operation_date | YYYY-MM-DD, ДД.ММ.ГГГГ, ДД/ММ/ГГГГ; Excel-дата |
| `amount` | Сумма, Сумма операции, Amount | Положительное число |
| `direction` | Направление, Направление операции | income / expense; поступление / списание; приход / расход; кредит / дебет |
| `counterparty` | Контрагент, Получатель, Плательщик, counterparty_name | Непустой текст |
| `inn` | ИНН, ИНН контрагента, counterparty_inn | Строка из 10 или 12 цифр; пропуск сохраняется как null с ошибкой |
| `description` | Назначение платежа, Описание, Description, payment_purpose | Непустой текст |
| `balance` | Остаток, Остаток на конец дня, balance_eod | Число, может быть отрицательным |

Английские имена всех полей поддерживаются. Регистр и лишние пробелы в
заголовках не учитываются. Неизвестные дополнительные столбцы не используются.
Необязательные `operation_id` и `company_id` сохраняются в `source_rows` для
сопоставления результата с исходной выпиской; они не становятся обязательными.
Повторяющиеся сопоставленные заголовки считаются неоднозначными.
Текстовые поля очищаются от лишних пробелов без удаления слов.
`id` генерируется с 1 при каждом успешном импорте; исходный порядок сохраняется.

Если столбца направления нет, допускаются два столбца `Поступление` и `Списание`
(также `income` / `expense`, `Кредит` / `Дебет`). В каждой строке ровно один
из них должен содержать положительную сумму; второй — ноль или пустую ячейку.
В этом случае общий столбец суммы необязателен; если он присутствует, значения
должны совпадать. Присутствующее, но пустое или неизвестное направление — ошибка.

Поддерживаются числа `15000`, `15000.50`, `15 000,50`, включая неразрывные пробелы.
Группы тысяч разделяются пробелами. Смешанные точка и запятая, валютные символы,
экспоненциальная запись и неоднозначные формы вроде `1.000,50` отклоняются.
Отрицательная сумма операции отклоняется, направление не выводится из знака.
Денежные значения внутри приложения — `Decimal`; в JSON они передаются строками
для сохранения точности, например `"15000.50"`. Финансовые расчеты через float
не выполняются.

ИНН проверяется по длине и цифрам; контрольная сумма и существование организации
не проверяются. В Excel храните ИНН именно текстом: ведущие нули, уже утраченные
в числовой ячейке, восстановить невозможно.

## API

`POST /api/transactions/upload` принимает multipart-поле `file`:

```powershell
curl.exe -X POST http://127.0.0.1:8000/api/transactions/upload -F "file=@data/sample.csv"
```

Сокращенный пример ответа для `sample.csv` (массив операций содержит 4 записи):

```json
{
  "status": "success",
  "message": "Выписка успешно обработана",
  "total_transactions": 4,
  "valid_transactions": 4,
  "invalid_transactions": 0,
  "duplicates": 0,
  "duplicate_groups": [],
  "errors": [],
  "warnings": [
    "Есть несколько операций за один день; остаток на конец дня не сверяется после каждой операции",
    "Арифметическая сверка остатков не выполнялась: не известны начальный остаток и полнота выписки"
  ],
  "transactions": [
    {
      "id": 1,
      "date": "2026-10-01",
      "amount": "15000.50",
      "direction": "income",
      "counterparty": "ООО Демо Клиент",
      "inn": "0000000001",
      "description": "Оплата демонстрационных услуг",
      "balance": "112000.00"
    }
  ]
}
```

Ошибки формата, структуры и данных возвращаются с HTTP 400:

```json
{"detail": "Некорректный ИНН: ожидается строка из 10 или 12 цифр в строке 2"}
```

Превышение лимита размера — HTTP 413, отсутствие multipart-поля — HTTP 422.
Номер строки включает заголовок; для многострочного CSV-поля это номер записи
таблицы, а не физической строки текста. Пустые строки не становятся операциями,
но учитываются в `source_row`. Ответ также содержит `source_rows`: для каждой
операции — `transaction_id`, `source_row`, исходные `operation_id` и `company_id`
(либо null, если идентификаторов нет).

Пустой ИНН — единственная восстанавливаемая ошибка данных: операция сохраняется
с `inn: null`, без выдуманного значения. Ответ HTTP 200 имеет `status:
"partial_success"`, `invalid_transactions` — число таких операций,
`valid_transactions` — число остальных; оба счетчика в сумме равны
`total_transactions` и длине `transactions`. Детали содержатся в `errors`:

```json
{
  "transaction_id": 2,
  "source_row": 3,
  "operation_id": "DEMO-002",
  "company_id": "DEMO",
  "field": "inn",
  "message": "Не заполнен ИНН; операция сохранена без подстановки значения"
}
```

`partial_success` означает наличие ошибок качества, все операции сохранены.
Непустой некорректный ИНН, отсутствие обязательного столбца, пустые другие
обязательные поля и ошибки дат/сумм по-прежнему отклоняют всю загрузку с HTTP 400.
Предыдущая успешно загруженная выписка при этом сохраняется. Успешная или
частично успешная загрузка заменяет ее целиком, без удаления отдельных строк.

`GET /api/transactions` возвращает массив последней успешно загруженной выписки,
до первого импорта — `[]`. Данные хранятся только в памяти экземпляра приложения:
новая успешная загрузка заменяет выписку, перезапуск очищает данные. Запускайте
один worker; при одновременных загрузках сохраняется последняя завершенная.
Для MVP нет разделения данных по пользователям и постоянного хранилища.

Дубликаты определяются по дате, сумме, направлению, контрагенту и назначению.
`duplicates` — число повторных записей сверх первой в каждой группе,
`duplicate_groups` — группы идентификаторов, например `[{"transaction_ids":[1,2]}]`.
Все операции сохраняются: одинаковые платежи могут быть реальными.

## Ограничения и следующий спринт

Проверяются даты и несколько операций за день; несортированный порядок вызывает
предупреждение. Остатки сохраняются из файла без пересчета. Арифметическая
сверка не выполняется: без начального остатка и подтверждения полноты выписки
достоверно проверить ее нельзя. Разный остаток у операций одного дня сам по
себе не делает файл некорректным.

Предоставленные C071.csv и C015.csv проверены полностью и имеют одинаковую
плоскую структуру, UTF-8 с BOM и разделитель `;`. Период обоих файлов:
2024-10-01 — 2026-09-30. C071 содержит 614 операций и 5 пустых ИНН;
C015 — 2455 операций и 96 пустых ИНН. Других пропусков обязательных полей и
потенциальных дубликатов не найдено. Оба файла возвращают `partial_success`;
все 3069 операций сохраняются при отдельных загрузках. Файлы не объединяются;
как и раньше, GET возвращает только последнюю загруженную выписку.

Не поддерживаются XLS, PDF, CP1251, выписки с преамбулой,
несколькими строками заголовка, объединенными ячейками и сложными формулами.
Формулы не вычисляются; пустой результат формулы в обязательном поле — ошибка.
Дополнительные форматы конкретных банков потребуют обезличенных примеров для
проверки заголовков, смысла дебета/кредита и момента фиксации остатков.

Типизированные операции, точные денежные значения, нормализованные даты и
направления используются отдельным сервисом категоризации Sprint 2.
Регулярность операций выявляется в Sprint 3. Прогнозы денежных потоков,
кассовые разрывы, вероятности, ML, dashboard, графики и внешние интеграции
не реализованы.

## Sprint 2: категоризация

Категории помогают отделять продажи и клиентские поступления от налогов,
зарплаты, услуг и собственных переводов. Назначения выполняются после загрузки;
исходные операции и ответы загрузчика не меняются.

Категории: продажи, поступления от клиентов, прочие поступления (явное страховое
возмещение), закупки, фонд оплаты труда, услуги по ГПХ, аренда, аренда
оборудования, налоги, банковские комиссии, маркетинг, коммунальные услуги,
связь и интернет, ПО и облачные услуги, хозяйственные и бухгалтерские услуги,
переводы между своими счетами, вывод средств предпринимателя, входящие и
исходящие возвраты. Резервная категория — `unknown` / «Не определено».
Категории логистики и «прочих расходов» не вводились: в предоставленных данных
нет достаточных оснований для таких правил. Возвраты как самостоятельные
операции предусмотрены алгоритмом, но в оригиналах не обнаружены.

Все правила и стабильные коды категорий находятся в
`backend/services/category_rules.py`. Текст только для поиска приводится к NFKC,
нижнему регистру, `ё` → `е`; пунктуация и повторяющиеся разделители заменяются
пробелами. Сам текст транзакции сохраняется. Анализируются направление,
назначение и, для общего правила комиссии, банковский контекст контрагента.
Сумма, дата, ИНН и остаток не изменяются и не используются как догадки о категории.

Побеждает правило с наибольшим явным приоритетом. Например, аренда POS имеет
приоритет над общей арендой, возврат — над обычной оплатой, вывод на личный счет
— над общим собственным переводом. Разные категории при одинаковом максимальном
приоритете дают `unknown` со статусом `needs_review`. Совпадения одной категории
не считаются конфликтом. Отсутствие правила дает `unknown` со статусом `undefined`.
Оба случая требуют ручного уточнения; автоматической подстановки «Прочее» нет.

Для каждой операции возвращаются метаданные по `transaction_id`: код и название
категории, версия источника `rules-v1`, статус (`automatic`, `undefined`,
`needs_review`), признак `is_automatic`, сработавшие правила и объяснение.
Проценты уверенности не вычисляются. Исходная модель Transaction не расширялась
финансовыми копиями; метаданные хранятся рядом с ней в памяти приложения.

После загрузки вызовите:

```powershell
curl.exe -X POST http://127.0.0.1:8000/api/transactions/categorize
```

Без тела или с `{}` категоризируется вся текущая выписка. Для выбора операций
передайте JSON `{"transaction_ids":[1,2]}` через Swagger `/docs` или HTTP-клиент.
Пустой список означает пустую выборку. Повторы ID дают HTTP 400,
несуществующие ID — 404, неверная структура JSON — 422. При пустом хранилище
возвращается сводка с нулевыми счетчиками и пустым массивом.

Пример полного ответа для выборки из одной операции оплаты клиентом:

```json
{
  "total_transactions": 1,
  "categorized_transactions": 1,
  "undefined_transactions": 0,
  "needs_review_transactions": 0,
  "automatic_percentage": 100.0,
  "distribution": {"customer_receipts": 1},
  "categorizations": [{
    "transaction_id": 1,
    "category": "customer_receipts",
    "category_name": "Поступления от клиентов",
    "source": "rules-v1",
    "status": "automatic",
    "is_automatic": true,
    "matched_rules": ["customer_payment"],
    "reason": "Совпадение правила по направлению и тексту"
  }]
}
```

`undefined_transactions` включает все операции без определенной категории;
`needs_review_transactions` — подмножество с конфликтами или неясным переводом.
`automatic_percentage` = число определенных категорий / число выбранных
операций × 100, округление до двух знаков; для пустой выборки — 0.

Повторный POST детерминированно обновляет метаданные тех же ID, не создает
транзакций и не удваивает суммы. Выборочная обработка сохраняет метаданные
остальных операций. GET `/api/transactions` возвращает прежние финансовые поля;
метаданные доступны в ответе POST категоризации. Новая успешная загрузка
(включая `partial_success`) очищает категории прошлой выписки, неудачная —
сохраняет их. Перезапуск очищает и выписку, и категории.

Правила v1 покрывают 614/614 операций C071 и 2455/2455 C015. Это покрытие,
не оценка точности: размеченных эталонных категорий нет. Проведена выборочная
проверка реальных операций каждой категории. Текст комиссии или возврата внутри
реестра эквайринга не меняет категорию зачисления «Продажи»; ГПХ не смешивается
с зарплатой, собственные переводы — с закупками.

Воспроизвести агрегированный отчет без копирования платежей:

```powershell
.\.venv\Scripts\python.exe -m scripts.analyze_categorization --dataset-dir "C:\Users\nises\Downloads\Telegram Desktop" --output docs/sprint2_results.json
```

Распределение и проверенные ссылки на исходные строки:
[sprint2_results.json](docs/sprint2_results.json). Подробности алгоритма, проверки
и ограничения: [sprint2.md](docs/sprint2.md). Новые банковские формулировки могут
остаться неопределенными или дать ошибочное совпадение; правила требуют проверки
при расширении данных. Интерфейс ручного редактирования категорий не добавлялся.

## Sprint 3: повторяющиеся операции

Модуль помогает найти повторяющиеся платежи и поступления без изменения
исходных транзакций. После загрузки выписки:

```powershell
curl.exe http://127.0.0.1:8000/api/transactions/recurring
```

GET использует текущую выписку и сохраненные категории Sprint 2. Для операций
без сохраненной категории вычисляет ее тем же сервисом только для анализа,
не изменяя хранилище категорий. Пустая выписка дает пустой список и нулевые
счетчики. Результат пересчитывается при каждом GET; кэширования и устаревших
результатов после загрузки новой выписки нет. Остальные endpoints не менялись.

Группировка: нормализованное название контрагента, ИНН, направление, категория
и нормализованное назначение. Неизвестная категория допускается. Совпадение
суммы или категории само по себе недостаточно. Номера разовых счетов, чеков,
реестров, даты, месяц платежа и хвосты сумм/НДС убираются только из текста поиска.
Номера договоров, объектов и этапы зарплаты сохраняются. Поэтому аренда разных
объектов, аванс и окончательный расчет не сливаются. Пустой ИНН не приравнивается
к известному, разные контрагенты не объединяются. Неинформативные назначения
вроде «Платеж» остаются одиночными ID.

Периоды: `weekly`, `biweekly`, `monthly`, `quarterly`, `yearly`, `unknown`.
Анализируются соседние интервалы и согласованность всей последовательности.
Для недели/двух недель допуск ±2 дня и проверка общей фазы ритма. Для месяца,
квартала и года — календарные циклы с типичным днем и допусками ±5/7/10 дней.
Не более 15% дат и не более 15% интервалов могут быть исключениями; числа
показываются в `date_exceptions` и `interval_exceptions`. Разрыв более трех
периодов (для недель с допуском) отвергает этот период. На двух-трех датах
исключения не допускаются. Две операции одного календарного цикла не доказывают
месячную регулярность; налоги с несколькими платежами в месяц остаются `unknown`.

Статусы:

- `confirmed`: минимум три разные даты, установленный ритм и нет нескольких
  платежей одной даты. Это подтверждение по правилам, не гарантия будущего платежа.
- `potential`: только две даты либо ритм есть, но несколько платежей проведены
  одной датой. Все исходные ID сохраняются; нужна проверка объединения.
- `uncertain`: поддерживаемая периодичность не установлена, следующая дата — null.

Средняя сумма — арифметическое среднее всех фактических сумм группы через Decimal,
округление до копеек HALF_UP; также возвращаются минимум и максимум. Если максимум
больше минимума в 1.5 раза, `amount_variable: true`: ритм может быть подтвержден,
но средняя сумма требует проверки. `usable_for_calculations: true` только для
`confirmed` с известной следующей датой и без такого разброса. Это технический
признак пригодности серии; прогноз денежных потоков не выполняется.

Следующая дата для недели/двух недель — последняя фактическая дата +7/+14 дней.
Для календарных периодов используется последний расчетный цикл и нижняя медиана
наблюдаемых дней месяца. Платеж у границы месяца сопоставляется с ближайшим
типичным днем; поэтому декабрьская досрочная выплата может относиться к январю.
Если все даты — последние дни месяцев, следующий день также последний; иначе
день ограничивается длиной месяца. Февраль и високосный год учитываются.
Перенос на рабочий день не выполняется. Дата рассчитана относительно истории,
может быть в прошлом и не переносится автоматически к сегодняшнему дню.

Ответ содержит счетчики групп и `groups`. Каждая группа включает `group_id`,
описание сравнения, контрагента, категорию, направление, период, статус,
`transaction_ids`, число операций и разных дат, среднюю/минимальную/максимальную
суммы, средний интервал в днях, первую/последнюю/следующую даты и объяснение.
Денежные значения — строки Decimal, как в Sprint 1. `average_interval_days`
учитывает все соседние операции, включая нулевые интервалы одной даты; для
проверки ритма рассматриваются разные даты без удаления исходных операций.
Одиночные операции перечислены в `ungrouped_transaction_ids`.

`total_groups` включает повторные кандидаты всех трех статусов. Это не счетчик
подтвержденных обязательств. В C071: 50 кандидатов, 6 confirmed, 4 potential,
40 uncertain. В C015: 25, 8, 4, 13 соответственно. Ежедневные зачисления C015
остаются unknown: дневной период не входит в поддерживаемую схему.
